## 1. 工作边界总则

### 1.1 阶段确认前置

Codex 在任何任务开始前，必须先确认当前任务属于哪个阶段。如果用户没有明确授权进入下一阶段，Codex 不得主动实现下一阶段功能。

### 1.2 阶段锁定

当前 Phase 只允许做当前阶段范围内的文档、设计、测试或代码。不允许因为某个未来功能"以后会用到"就提前写代码或预留接口。

### 1.3 范围蔓延禁止

用户提出超出当前阶段的需求时，Codex 必须：
1. 指出该需求属于哪个阶段
2. 记录到对应阶段的待办清单中
3. 不得在当前阶段实现

## 3. 恢复验证优先原则

### 3.1 完成标准

任何功能在没有明确、可验证的恢复路径之前，不能标记为完成。验收标准以恢复验证为准，而非"备份任务完成"。

### 3.2 测试要求

所有开发任务必须包含以下测试场景：

| 测试类型 | 要求 |
|---------|------|
| 正向路径测试 | 正常数据可备份、可恢复 |
| 失败路径测试 | 目标盘空间不足、源文件被锁定等 |
| 中断/异常路径测试 | 备份过程中断后不破坏已有备份 |
| 恢复验证测试 | 恢复后数据与源数据 SHA-256 一致 |
| 数据一致性验证 | 批量小文件、大文件、空目录、特殊字符文件名 |
| 日志和错误信息验证 | 错误可理解、可定位 |

### 3.3 恢复验证层级

`
文件级：  恢复后文件 checksum 一致
卷级：    恢复后卷可挂载，文件系统通过，抽样文件 hash 一致（Phase 2+）
系统级：  恢复后系统可启动、登录、识别系统盘（Phase 3+）
异机还原：恢复后系统在不同硬件上可启动、无蓝屏（Phase 5+）
`

## 4. 文档变更规则

### 4.1 变更必须记录

任何文档变更必须：

1. 更新版本号
2. 更新 Revision History（在文档末尾）
3. 明确本次变更原因
4. 明确是否影响开发计划
5. 明确是否影响验收标准
6. 不得让不同文档之间出现互相矛盾的范围描述

### 4.2 一致性检查

修改任何文档后，必须检查其他文档是否有冲突内容。发现冲突必须同步修正或明确标记为"待更新"。

## 5. Codex 汇报规则

每次任务完成后，必须输出：

1. **修改了哪些文件** — 完整清单
2. **每个文件修改了什么** — 主要变更摘要
3. **哪些专家审查意见已落实** — 逐条对应
4. **哪些内容被降级为 Future** — 详细清单
5. **哪些内容被禁止当前阶段实现** — 明确范围
6. **当前阶段是否仍然保持范围收敛** — 是/否 + 说明
7. **是否仍有文档冲突** — 如有，列出冲突点

## 6. 数据完整性高于速度

性能优化可以后置。第一阶段（Phase 1~2）优先级顺序：

| 优先级 | 目标 |
|--------|------|
| 1 | 数据不丢 |
| 2 | 可校验 |
| 3 | 可恢复 |
| 4 | 中断后不破坏已有可用备份 |
| 5 | 用户不会误操作覆盖关键数据 |
| 6 | 性能优化 |

---

## 7. 先闭环，再扩展

必须先完成一个最小可验证的备份/恢复闭环，再进入镜像格式、卷级、系统级、WinPE、克隆、异机还原等复杂能力。

| 顺序 | 闭环内容 |
|------|---------|
| 第 1 个闭环 | 文件级：选择文件 → 备份 → 选择恢复点 → 恢复 → SHA-256 一致 |
| 第 2 个闭环 | 文件夹级：多级目录、空目录、特殊字符处理 |
| 第 3 个闭环 | 跨设备恢复：备份到 USB → 恢复到另一台机器 |
| 后续闭环 | 由阶段扩展逐步引入 |
